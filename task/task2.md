## Step 0 — shared contract ✅ done (on `main`)

Already built and tested. Every agent builds on these files and **must not change them**.

**Things to know before you start:**
- `Product.quantity` is **read-only for JPA** (`insertable = false, updatable = false`, no setter): new
  products start at 0, and saving a `Product` you loaded earlier can never overwrite the stock.
  After a stock change, a `Product` already loaded in memory still shows the old number.
- `ProductStockService.increase/decrease` require an **existing transaction**
  (`Propagation.MANDATORY`) — call them from a `@Transactional` method that also writes the movement.
- `PurchaseOrder.poNo` is generated by the database on insert (`PO-000001`) — don't set it.
- `CatalogFixtures` is a bean in every `IntegrationTest`: `@Autowired CatalogFixtures fixtures;`
  then `fixtures.category(..)`, `fixtures.supplier(..)`, `fixtures.product(category, name, price, qty, minStock)`,
  `fixtures.quantityOf(product)`, `fixtures.manager()` (a user for `created_by`).
- New ArchUnit rule `onlyStockServiceChangesProductQuantity`: only
  `com.psar.inventory.service.StockService` may use `ProductStockService`.
- Example tests: `catalog/service/ProductStockServiceTest` (incl. 10 buyers / 3 left at the
  repository level), `inventory/service/Step0InventorySchemaTest`.

### 1. `V2__catalog_and_inventory.sql`

| Table | Columns (all have `id BIGSERIAL`, `created_at`, most have `updated_at`) |
|---|---|
| `categories` | `name` VARCHAR(100), `name_kh`, `slug` UNIQUE, `parent_id` → categories (NULL = top level), `image_url`, `sort_order`, `is_active` |
| `suppliers` | `public_id` UUID UNIQUE, `name`, `phone`, `email`, `address` TEXT, `note`, `is_active` |
| `products` | `public_id` UUID UNIQUE, `sku` UNIQUE, `name`, `name_kh`, `slug` UNIQUE, `description` TEXT, `category_id` → categories, `supplier_id` → suppliers (nullable), `cost_price` NUMERIC(12,2) ≥ 0 (**required, no default**), `sell_price` NUMERIC(12,2) > 0, `quantity` INT ≥ 0 DEFAULT 0, `min_stock` INT ≥ 0 DEFAULT 10, `unit` VARCHAR(20), `is_active` |
| `product_images` | `public_id` UUID UNIQUE, `product_id` → products ON DELETE CASCADE, `image_url`, `storage_key`, `is_main`, `sort_order`; **partial unique index: one main image per product** |
| `stock_movements` | `product_id`, `type` (IN/OUT/ADJUST), `quantity` INT ≠ 0 (**signed**: + adds, − removes), `balance_after` INT ≥ 0, `reason` (PURCHASE/ORDER/RESERVE/RELEASE/CANCEL/DAMAGE/RETURN/CORRECTION/REWARD), `reference_id` (e.g. PO id), `note`, `created_by` → users, `created_at` only |
| `purchase_orders` | `po_no` UNIQUE (from sequence `po_no_seq` → `PO-000001`), `supplier_id`, `status` (PENDING/RECEIVED/CANCELLED), `total_amount` NUMERIC(12,2), `note`, `created_by` (**NOT NULL**), `received_at`, `cancelled_at` |
| `purchase_order_items` | `purchase_order_id` ON DELETE CASCADE, `product_id`, `quantity` > 0, `unit_cost` NUMERIC(12,2) ≥ 0, UNIQUE (`purchase_order_id`, `product_id`) |

Indexes: `products(category_id)`, `products(is_active)`, `stock_movements(product_id, created_at)`,
`purchase_orders(status)`. **`products.quantity` has `CHECK (quantity >= 0)`** — the last line of
defence against overselling.

Differences from `architecture.md` (deliberate): `public_id` on products, suppliers and images
(CLAUDE.md: never expose `id`); `CORRECTION` reason (PRD lists "correction" adjustments);
signed `quantity` + `balance_after` so history reads like a bank statement.

### 2. Entities + enums
`catalog/entity`: `Category`, `Product`, `ProductImage`.
`inventory/entity`: `Supplier`, `StockMovement`, `MovementType`, `MovementReason`, `PurchaseOrder`,
`PurchaseOrderStatus`, `PurchaseOrderItem`.
Cross-module references are plain IDs (like `Address.deliveryCompanyId`): `Product.supplierId`,

### 3. Repositories — one per entity, with lookups by `publicId` / `slug` / `poNo` and the stock queries in `ProductRepository`.

### 4. Cross-module services (the only way modules touch each other here)

**`catalog/service/ProductStockService`** — used **only** by inventory's `StockService`
(enforced by a new ArchUnit rule). Changes `products.quantity` with one atomic SQL each:
```java
ProductStockInfo require(UUID productPublicId)        // 404 if missing
ProductStockInfo require(Long productId)
int increase(Long productId, int qty)                 // returns new quantity
int decrease(Long productId, int qty)                 // UPDATE ... WHERE quantity >= :qty;
                                                      // 0 rows → ConflictException(INSUFFICIENT_STOCK)
Page<ProductStockInfo> lowStock(Pageable)             // active, quantity <= min_stock
```
`ProductStockInfo` (record in `catalog/dto/response`): `id, publicId, sku, name, quantity, minStock, active`.

**`inventory/service/SupplierService`** — Step 0 creates two methods for Agent A; Agent B adds the rest:
```java
Long requireActiveId(UUID supplierPublicId)                    // 422 if missing/inactive
Map<Long, SupplierSummary> summaries(Collection<Long> ids)     // publicId + name, for admin product lists
```

### 5. `ErrorCode` additions
`INSUFFICIENT_STOCK` (409), `SKU_ALREADY_EXISTS` (409), `INVALID_STATUS` (409, e.g. receiving a cancelled PO).

### 6. Test support
`src/test/java/com/psar/support/CatalogFixtures` — `category(name)`, `supplier(name)`,
`product(category, sku, sellPrice, quantity, minStock)` saved through repositories with unique
names/SKUs. Agents A and C both need products in their tests.

## Agent A — Catalog (categories, products, storefront)

### Build
- **Slugs** (`catalog/service/SlugGenerator`): lowercase, ASCII, hyphens (`"Fresh Milk 1L"` → `fresh-milk-1l`);
  if the name has no Latin letters (Khmer only) use the SKU; on clash add `-2`, `-3`…
  A product/category keeps its slug when renamed (links don't break).
- **`CategoryService`**: two levels only (a subcategory can't have children → 422). Delete = soft
  (`active=false`); refuse while it has active products or active subcategories → 422.
- **`ProductService`**:
  - Create: SKU trimmed + uppercased, duplicate → 409 `SKU_ALREADY_EXISTS`; category must exist and be active;
    supplier via `SupplierService.requireActiveId` (optional field). **Quantity always starts at 0** —
    stock only enters through a purchase order or adjustment (Agent C), so every unit has a movement row.
  - Update: everything except `quantity` (not in the request DTO). Delete = soft.
  - Money: `BigDecimal`, scale 2, `sellPrice > 0`, `costPrice >= 0`.
- **Public storefront** (no login): only active products in active categories.
  `ProductResponse` / `ProductDetailResponse` **never contain `costPrice`, `supplier` or exact `quantity`** —
  only `inStock` (quantity > 0). Admin responses (`AdminProductResponse`) include them.
- Search/filters with a `Specification`: `q` (name or SKU, case-insensitive), `category` slug
  (**includes its subcategories**), `minPrice`, `maxPrice`, `inStock`. Sort allowlist:
  `newest` (default), `price_asc`, `price_desc`, `name`. Page size max 100.
- List responses include the main image URL (read `ProductImageRepository`, one query per page — no N+1).

## Agent B — Images, storage & suppliers

### Build
- **`pom.xml`**: Cloudinary Java SDK (`com.cloudinary:cloudinary-http5`).
- **`common/storage/StorageService`** (in `common`: avatars, delivery logos and AI documents will reuse it):
  `StoredFile upload(String folder, MultipartFile file)` → `{key, url}`; `void delete(String key)`.
  Files go to Cloudinary through a `FileStore` (`CloudinaryFileStore`); config `app.storage.cloudinary-url`
  (`CLOUDINARY_URL`) and `app.storage.folder` (root folder: `psar-dev` / `psar`). The key is the Cloudinary
  public ID, e.g. `psar/products/{uuid}` — never the user's file name.
- **Upload validation**: JPEG / PNG / WebP only, checked by **file signature (magic bytes)**, not the
  `Content-Type` header → 415 `UNSUPPORTED_MEDIA_TYPE`; max 5 MB → 413 `PAYLOAD_TOO_LARGE`.
- **`ProductImageService`**: first image becomes main; one main per product; max 10 images (422);
  delete main → next by `sort_order` becomes main; delete the stored file **after the transaction
  commits** (`@TransactionalEventListener(AFTER_COMMIT)`), so a rollback never leaves a DB row
  pointing to a deleted file.
- **`SupplierService`** (keep the Step 0 methods): list (`q`, `active`), get, create, update,
  soft delete (refuse while it has PENDING purchase orders → 422; read `PurchaseOrderRepository`).
- **`TestcontainersConfiguration`**: an in-memory `FileStore` (`@Primary`), since Cloudinary has no local
  emulator — integration tests never call Cloudinary.

## Agent C — Stock & purchase orders

### Build
- **`StockService`** — the **only** code that changes stock (CLAUDE.md rule). Each method calls
  `ProductStockService.increase/decrease` and writes the `stock_movements` row (with `balance_after`,
  `created_by`) **in the same `@Transactional`**:
  ```java
  void receive(Long productId, int qty, MovementReason reason, Long referenceId, Long userId)   // IN
  void remove(Long productId, int qty, MovementReason reason, Long referenceId, Long userId)    // OUT, 409 if not enough
  void adjust(UUID productPublicId, int change, MovementReason reason, String note, Long userId) // ADJUST
  ```
  Phase 4 checkout will call `remove(..., RESERVE, orderId, …)`, so keep it general.
- **Adjustments**: `change ≠ 0`; reason must be `DAMAGE`, `RETURN` or `CORRECTION`; result below 0 → 409 `INSUFFICIENT_STOCK`.
- **`PurchaseOrderService`**:
  - Create: supplier active, ≥ 1 item, products exist (by `publicId`), the same product twice → 400,
    `quantity > 0`, `unitCost >= 0`; **`totalAmount` calculated on the backend** (Σ qty × unitCost, HALF_UP, scale 2).
  - Receive: only PENDING → each item `StockService.receive(PURCHASE, poId)`, status RECEIVED, `receivedAt`.
    Lock the PO row (`PESSIMISTIC_WRITE`) so a double click or two managers can't receive it twice.
  - Cancel: only PENDING → CANCELLED. Receiving/cancelling a non-PENDING PO → 409 `INVALID_STATUS`.
- **Movements**: filter by product, type, reason, date range; newest first.
- **Low stock**: `ProductStockService.lowStock(...)` → list for the dashboard (alerts come in Phase 3/9).

## Rules for every agent

Same as Task 1: follow `CLAUDE.md`; constructor injection; thin controllers; `@Transactional` on
writing service methods; DTO records only; lists paginated (max 100) with a sort allowlist;
test names `methodName_condition_expectedResult`; integration tests extend `IntegrationTest`
and use unique names/SKUs. No `Co-Authored-By` lines. Don't touch Flyway — need a schema change? Ask the lead.
Before finishing: `cd backend && ./mvnw test` passes; endpoints look right in Swagger.

## Merge order

1. Step 0 → `main`.
2. Agents work in parallel from that `main`.
3. Suggested merge order: **B → A → C** (B changes `pom.xml` and test config that everyone's tests run on).
   After each merge, the next branch rebases on `main` and re-runs `./mvnw test`.
4. After all three, one end-to-end test on `main`: supplier → category → product (stock 0, shown as
   out of stock) → upload image → purchase order → receive → storefront shows it in stock with its
   main image → damage adjustment → movement history shows both rows → product appears in low stock.
